- [ ] **Typing into a time field gets randomly overwritten mid-keystroke** (observed 2026-08-24, manual testing during the Gradio upgrade). Root cause: `_start_time`/`_arrival_time` (`durees.py`) are plain `gr.Textbox` fields that are both `.input` triggers *and* members of `all_outputs` for the same `_compute` chain (`durees.py:161-162, 211-222`). `_compute` always returns a value for every output — including an unchanged echo of whichever field is being typed into (e.g. `durees.py:56`) — and Gradio pushes that back to the client on every keystroke regardless of whether it changed. Because the round-trip isn't instant, the echoed value is a stale snapshot of what was typed a keystroke or two ago, clobbering what's been typed since. Already hit this same class of bug in `ArmyInputHTML` (see [[project_army_input_html]]) and in Playwright tests (see `feedback_gradio_textbox_fill.md`'s `keyboard.type` warning) — this is the first time it's been noticed as a live UX problem rather than a test-writing gotcha.

Worth investigating both before picking one.

    - Wheel-scroll "missed ticks" investigation (2026-08-25): root cause is confirmed to be Firefox's APZ (Asynchronous Panning and Zooming) content round-trip, not event coalescing tied to display refresh rate. A non-passive `wheel`/`touchmove` listener (required here since we call `preventDefault()`) makes APZ wait for a response from the content process before it'll trust our `preventDefault()` decision — deadline is 400ms on desktop, 600ms on mobile ([Firefox source docs](https://firefox-source-docs.mozilla.org/gfx/AsyncPanZoom.html)), and further physical wheel notches queue/coalesce (summed, not dropped — verified empirically) behind that round-trip. This is an architectural ceiling for any Firefox wheel-hijacking widget, not something fixable by making our handler faster (already tried — patched `render()` to update segment text in place instead of rebuilding the DOM per tick; didn't move the needle, as expected once the real mechanism was understood). Current state, all marked `TEMP EXPERIMENT` in `script.js`:
      - A `deltaY`-magnitude-scaled step count recovers the coalesced total correctly (verified against synthetic multi-notch deltas), scaled by a **self-calibrating per-notch unit estimate** rather than a hardcoded constant (an earlier hardcoded 102 broke immediately on a second physical mouse — no cross-hardware standard for pixels-per-notch exists at the browser-JS level, see the comment block above `widget.addEventListener('wheel', ...)` for the full writeup and sourcing). Calibration tracks the running *minimum* observed `|deltaY|`, reset after 200ms idle — mirroring the long-established jQuery Mousewheel plugin's `lowestDelta` pattern (deliberately not GCD, which was considered and rejected: GCD is corrupted by a sample landing on *either* side of the true unit, min-tracking only by one landing *below* it).
      - The highlight-pulse animation experiment (masking jumps as continuous-feeling motion) was tried and reverted — no perceptible improvement in manual testing, and the actual goal turned out to be *consistency* (a round-trip scroll returns to the same value) rather than visual smoothness, which the calibration approach addresses directly.
      - Known open edge case, deliberately not chased (not representative of normal usage): rapidly alternating up/down scrolling was observed to drift the value in one direction over time rather than cancelling out exactly. Root cause not identified — the leading hypothesis (asymmetric `Math.round()` behavior at `.5` boundaries) was tested and ruled out, since the reporter's hardware only ever produces exact multiples of its true per-notch unit, leaving no rounding error once calibration converges. Revisit if it turns out to matter in practice.
      - Touch/mobile already declares `touch-action: none` (`style.css`) — the one declarative escape hatch Mozilla's docs recommend for this exact APZ tax — but wheel has no equivalent CSS opt-out, so coarser-than-ideal wheel granularity may just be a ceiling to design around rather than solve outright.
    - A full code-review + simplify pass (2026-08-25, both delegated to subagents, both effort "high") went through the whole branch; all findings from both were fixed except one deliberately skipped efficiency item: threading a precomputed `displayState` through `render()`/`commit()`/`formatState()`'s call chain to avoid recomputing it 2-3x per tick — the arithmetic itself is cheap and the signature changes would touch many call sites for little real gain, so judged not worth it. Everything else (paste-parsing now routed through a `server_functions` call to `nm.utils.parse_ajhms` instead of a duplicate JS parser; segment metadata now Python-owned via `data-seg-meta` instead of independently re-declared in JS; button styling matched to `ArmyInputHTML`/`LevelsInputComponent`'s shared look; assorted dead code/duplication/hot-path caching cleanups) is done and verified (full suite green, plus live Playwright checks for anything not already covered by the test suite).

## Documentation conventions

- [ ] **Define a convention for hybrid human/AI code documentation, then refactor to match it.** A human reading code has small context but infers a lot from little; an AI agent (Claude) has much more context available per-session but none carried over between sessions, so it needs the "why"/design-rationale spelled out explicitly to avoid re-introducing bugs it already fixed once (e.g. the synchro tab's BBCode-link-in-shared-DataFrame bug). What's "enough" documentation differs a lot between the two audiences, and this project has no established docstring/comment convention to build on (most functions have none, by design — code is meant to be readable at a glance). Pattern applied twice now in `src/nmsite/tabs/synchro.py` (2026-08-23): `format_copy_data_table` first, then `format_copy_data_discord`/`_format_discord_row`/`_discord_row_widths` — short, caller-focused docstrings (what a function does) plus inline comments at the exact line each design decision applies to (why), rather than one dense docstring or a separate linked doc file. Consistent enough now to call a working pattern, not yet a written-down, generalizable guideline. Next steps: (1) look at what other projects/teams do for hybrid human/AI documentation for inspiration, (2) write the actual guideline once informed by that, (3) refactor the rest of the codebase's docstrings/comments to match (most files haven't been touched yet — this has so far only been applied where Claude happened to be already working).
